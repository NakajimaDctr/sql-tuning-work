# Stage 1: EXPLAINの読み方

## このステージでわかること

SQLチューニングの第一歩は「今のクエリが遅い理由を説明できる」こと。
そのための道具が `EXPLAIN` で、クエリを実行する前にMySQLが立てた**段取り（実行計画）**を見せてくれる。
このステージでは `EXPLAIN` の主要なカラムの意味を覚え、
「速いクエリ」と「遅いクエリ」を出力から見分けられるようになる。
インデックスの追加はまだ行わず、「読む」ことに集中する。

## 前提

[Stage 0: 環境構築](../00_setup/README.md) が完了していること。

以下でMySQLに接続しておく。

```bash
docker compose exec mysql mysql -uroot -prootpass sqltuning
```

## どんな問題？ ― 身近な例えで

巻末に索引（さくいん）のない分厚い専門書から、ある1語を探す場面を想像してほしい。
索引がなければ、1ページ目から順番にめくって、全ページを目で追うしかない。
探している語が1か所しか出てこなくても、「1か所しかない」と確信するには結局最後まで見る必要がある。

データベースも同じで、**インデックス（＝索引）がない列で検索すると、MySQLはテーブルの全行を
1件ずつ確認する**しかない。これを「フルテーブルスキャン」と呼び、EXPLAINでは `type: ALL` と表示される。
`orders` テーブルは約50万行あるので、`type: ALL` は「50万回ページをめくる」のと同じことになる。

`EXPLAIN` は、MySQLが「索引を使えるのか、それとも全ページめくるのか」をどう判断したかを
教えてくれる、いわばクエリの**設計図・段取り表**である。

## まず現状を見てみる

`EXPLAIN` は普段の `SELECT` の頭に付けるだけで使える。実際には行を返さず、計画だけを表示する。

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
```

出力はおおよそ次のようになる（幅の都合で一部の列は省略）。

```
+----+-------------+--------+------+---------------+------+--------+-------------+
| id | select_type | table  | type | possible_keys | key  | rows   | Extra       |
+----+-------------+--------+------+---------------+------+--------+-------------+
| 1  | SIMPLE      | orders | ALL  | NULL          | NULL | 498521 | Using where |
+----+-------------+--------+------+---------------+------+--------+-------------+
```

**【ここを見る】**

| カラム | この行の値 | 読み方 |
|---|---|---|
| `type` | `ALL` | フルテーブルスキャン。全行を1件ずつ確認する、最も遅いアクセス方法 |
| `possible_keys` | `NULL` | 使えそうなインデックスの候補すら存在しない |
| `key` | `NULL` | 実際に使われたインデックスもなし |
| `rows` | `498521` | 「このクエリのために約49万行を調べる」というMySQLの見積もり。`orders`の全行数にほぼ等しい＝実質「全部見ている」 |
| `Extra` | `Using where` | ストレージエンジンから受け取った行に、サーバー側でさらに `user_id = 100` の条件をかけてふるい落とした |

`user_id = 100` に実際にヒットする行は数件〜十数件しかない。
それでも `user_id` にインデックスがないため、MySQLは全行を確認するしかない。これが「遅いクエリ」の典型例。

## いろいろなクエリのEXPLAINを見比べる

次の4つを順に実行し、`type` / `key` / `rows` / `Extra` がどう変わるかを見ていく。

```sql
-- Q1. 主キーでの検索
EXPLAIN SELECT * FROM users WHERE id = 100;

-- Q2. 主キー以外の列での検索（インデックスなし）
EXPLAIN SELECT * FROM orders WHERE user_id = 100;

-- Q3. インデックスのない列への文字列検索
EXPLAIN SELECT * FROM users WHERE email = 'user012345.johndoe@example.com';

-- Q4. 複数条件のAND検索（どちらの列にもインデックスなし）
EXPLAIN SELECT * FROM products WHERE category_id = 5 AND price > 1000;
```

**【結果の見方】** 想定される値と、その意味は次のとおり。

| # | `type` | `key` | `rows`(概算) | `Extra` | 何が起きているか |
|---|---|---|---|---|---|
| Q1 | `const` | `PRIMARY` | 1 | | 主キー `id` で1行に確定する。索引の一番得意な形。最速 |
| Q2 | `ALL` | `NULL` | 約498,000 | `Using where` | `user_id` に索引がなく全行スキャン |
| Q3 | `ALL` | `NULL` | 約48,000 | `Using where` | `email` に索引がなく全行スキャン。**1件しかヒットしないのに約4.8万行を調べる** |
| Q4 | `ALL` | `NULL` | 約10,000 | `Using where` | 条件が2つあっても、どちらの列にも索引がなければ全行スキャン |

### `type` の速さの序列

左ほど速く、右ほど遅い。

```
system / const  >  eq_ref  >  ref  >  range  >  index  >  ALL
```

- `const` … 主キー／ユニークキーで1行に確定（Q1）
- `eq_ref` … JOINで相手側が1行に確定するユニークキー参照（Stage 6で登場）
- `ref` … 非ユニークインデックスでの等値検索（Stage 2で `ALL` からここへ改善する）
- `range` … インデックスを使った範囲検索（`BETWEEN` `<` `>` `IN` など）
- `index` … インデックス全体は読むが、テーブル本体は読まない
- `ALL` … フルテーブルスキャン。**これが出たら、まず索引を検討する合図**

### `rows` は「返る件数」ではなく「調べる件数」

Q3 は実際には1件しか返らないクエリなのに、`rows` は約48,000だった。
`rows` は「**結果として返る行数**」ではなく「**答えを出すためにアクセスする行数の見積もり**」である。
索引がなければ、結果が1件でも全件確認が必要になる。
「結果の少なさ」と「スキャン量」は無関係だと理解しておくと、次のStage 2で索引の効果が腑に落ちる。

（`rows` はあくまで見積もりで、実際の値と完全一致するとは限らない。その理由はStage 5で詳しく扱う。）

## まとめ

- `EXPLAIN SELECT ...` でクエリの実行計画（段取り）を、実行前に確認できる
- `type` がアクセス方法を表し、`ALL`（フルスキャン）が出たら要注意
- `key` が `NULL` なら、インデックスが1つも使われていない
- `rows` は「調べる行数の見積もり」。結果件数とは別物
- `Extra` の `Using where` は「サーバー側で追加のふるい分けをした」の意味

## さらに詳しく

次の2つのクエリはどうなるか。実行して確かめてみると理解が深まる。

```sql
EXPLAIN SELECT COUNT(*) FROM orders;
EXPLAIN SELECT * FROM orders ORDER BY id DESC LIMIT 10;
```

- `SELECT COUNT(*) FROM orders` … `type` は `index` になりやすい。
  行の中身は要らず「件数」だけ分かればよいので、テーブル本体ではなく主キーインデックスを
  端から数えるだけで済む。`Extra` に `Using index`（インデックスだけで完結）が出る。
- `ORDER BY id DESC LIMIT 10` … 主キーインデックスは `id` の昇順に並んでいる。
  それを**逆から**10件たどれば済むので、`type` は `index`、`Extra` に `Backward index scan` が出て、
  `Using filesort`（別途の並べ替え）は発生しない。「並び順が索引と一致していればソートは要らない」という、
  Stage 4・9で効いてくる考え方の予告編。
