# Stage 1 補足 FAQ ― EXPLAIN と索引の仕組み

[Stage 1: EXPLAINの読み方](./README.md) を読んでいて出てくる疑問を、Q&A形式でまとめたもの。
「`type` の並び順は覚えたが、なぜそうなるのかが腑に落ちない」という段階の人向け。

---

## Q1. ストレージエンジンとは何か

MySQL は内部が大きく2階建てになっている。

```
┌─────────────────────────────────────────┐
│ SQLサーバー層（2階）                       │
│  ・SQLの構文解析                           │
│  ・実行計画を立てる（EXPLAIN が見せる部分）    │
│  ・受け取った行に最終的な条件をかける（Using where）│
├─────────────────────────────────────────┤
│ ストレージエンジン層（1階）  ← これ           │
│  ・ディスク／メモリ上の行データの管理           │
│  ・インデックス（B+木）の保持と探索            │
│  ・トランザクション・ロック・バッファ管理        │
└─────────────────────────────────────────┘
```

サーバー層が「`user_id = 100` の行が欲しい」と注文し、ストレージエンジンが該当行を取ってきて返す、という分業。
テーブルごとに `CREATE TABLE ... ENGINE=InnoDB` で選べる。

| エンジン | 特徴 |
|---|---|
| **InnoDB** | 現在の標準。トランザクション・行ロック・外部キー・クラッシュリカバリ対応。この教材のテーブルは全部これ |
| MyISAM | 旧標準。トランザクションなし・テーブルロックのみ。現在はほぼ使わない |
| MEMORY | データをメモリ上だけに持つ。高速だが再起動で消える |

### Stage 1 とのつながり

`Extra` の `Using where` はこの2階建て構造そのものを表す。

- ストレージエンジン（InnoDB）が `orders` の全行をサーバー層へ渡す
- サーバー層が受け取った行に `user_id = 100` を当てて、ほとんどを捨てる

インデックスがあれば、この絞り込みをストレージエンジン層で先にできるので、
サーバー層に渡る行数自体が激減する。「どちらの層で行を絞るか」がチューニングの肝。

## Q2. `type` はどんな条件で変わるのか

おおむね次の3要素の掛け算で決まる。

1. **検索する列にインデックスがあるか**（なければ問答無用で `ALL`）
2. **そのインデックスが PRIMARY / UNIQUE か、非ユニークか**（1行に確定できるか）
3. **条件の形**（`=` なのか、`>` `<` `BETWEEN` `IN` `LIKE 'x%'` なのか）

これに JOIN の文脈が加わる。速い順に条件を並べると次のとおり。

| `type` | この値になる条件 | 例 |
|---|---|---|
| `const` / `system` | PRIMARY か UNIQUE に定数で `=`、1行に確定 | `WHERE id = 100` |
| `eq_ref` | JOIN で結合相手が PRIMARY / UNIQUE により必ず1行に決まる | `JOIN users u ON u.id = o.user_id` |
| `ref` | 非ユニークインデックス（複合の一部含む）に `=` | `WHERE user_id = 100`（索引追加後） |
| `range` | インデックス列に範囲条件 | `>` `<` `>=` `<=` `BETWEEN` `IN (...)` `LIKE 'abc%'` |
| `index` | インデックスを端から端まで全走査。テーブル本体は読まないことが多い | `SELECT COUNT(*)`、`ORDER BY id LIMIT 10` |
| `ALL` | 使えるインデックスがない。全行スキャン | `WHERE email = 'xxx'`（email に索引なし） |

### 注意点

- **インデックスがあっても `range` / `ref` にならないことがある**。ヒット件数が多すぎる（例：全体の3割）と、
  オプティマイザが「全部読んだ方が速い」と判断して `ALL` を選ぶ。→ Stage 5。
- **列を加工すると索引が効かず `ALL` に落ちる**。`WHERE DATE(created_at) = '2024-01-01'`、
  `WHERE user_id + 0 = 100` など、関数や計算をかけた瞬間にインデックスが使えなくなる。
- **`LIKE '%abc'`（後方・中間一致）は `range` にならない**。前方一致 `'abc%'` だけがインデックスで範囲検索できる。
- **複合インデックスは「左から連続して」使えた分だけ効く**。`(a, b, c)` に対し `WHERE a = ? AND b = ?` は使えるが、
  `WHERE b = ?` 単独では使えない。→ Stage 4。
- **`type` は「1テーブルあたり」の評価**。JOIN すると EXPLAIN の行がテーブルごとに出て、それぞれに `type` が付く。

## Q3. `type: index` は意外と遅い？

そのとおり。序列でも下から2番目。

```
const > eq_ref > ref > range > index > ALL
                                ↑ここ
```

`index` は「インデックスを端から端まで全部読む」アクセス。やっていることは全走査で、
`ALL` の走査対象がテーブル本体からインデックスに変わっただけ。件数で絞る力は持っていない。

速いか遅いかは **テーブル本体を読むかどうか** で決まる。

| ケース | `Extra` | 速さ |
|---|---|---|
| インデックスだけで答えが出る（カバリング） | `Using index` | `ALL` よりは速い。索引は本体より小さいので読む量が減る |
| 1件ずつテーブル本体に取りに戻る | （なし） | **`ALL` より遅くなりうる**。行ごとにランダムアクセスが発生する |
| `LIMIT` で途中で打ち切れる | | 速い。全部読まず必要な分でやめられる |

`index` が出たら「速くなった」ではなく「まだ全走査している」と読む。
救いがあるのは `Using index`（カバリング）か `LIMIT` が付いているとき。

## Q4. `SELECT COUNT(*)` は速いのに `SELECT * ... ORDER BY user_id` が遅いのはなぜか

両方とも `type: index` だが、走査したあとの仕事量が全然違う。
`type` はアクセスの入口の形しか表さないので、ここが落とし穴。

### 前提：InnoDB のインデックスに何が入っているか

`orders`（`id` が主キー）に `user_id` のインデックス `ix_user_id` を張ったとする。

```
■ クラスタインデックス（＝テーブル本体）   id順に並ぶ
  id=1 | user_id=100 | status=paid | total_amount=3000 | created_at=...
  id=2 | user_id=55  | status=new  | total_amount=1200 | created_at=...
       └─ 全列がここに揃っている

■ ix_user_id（セカンダリインデックス）    user_id順に並ぶ
  user_id=55  → id=2
  user_id=100 → id=1
  user_id=100 → id=3
       └─ 入っているのは user_id と id だけ。他の列はない
```

セカンダリインデックスには「張った列」＋「主キー」しか入っていない。これが鍵。

### `SELECT COUNT(*)` が速い理由

- 必要なのは件数だけ。列の値は1つも要らない。
- 一番小さいインデックスを選び、その葉を端から端まで順番になぞって数えるだけ。
- インデックスはディスク上で並んで置かれているので **連続読み込み（シーケンシャル）**。速い。
- テーブル本体には一切触らない → `Extra: Using index`。
- 返すのは数字1個。

### `SELECT * ... ORDER BY user_id` が遅い理由

`SELECT *` なので `status` `total_amount` `created_at` も必要。でも `ix_user_id` には入っていない。

1. `ix_user_id` を端からなぞって、`user_id` 順の `id` 列を得る（ここまでは速い）
2. **1件ごとに、その `id` を持ってテーブル本体へ取りに戻る**（回表）
3. これを **50万回** 繰り返す

問題は 2 の「取りに戻る」がランダムアクセスなこと。
`user_id` 順にたどるので飛んでいく `id` はバラバラ。ディスク上の離れた場所へ50万回ジャンプする。
連続読み込みの何倍も遅い。さらに返す行も50万行フル。

```
ix_user_id をなぞる       本体へジャンプ（ランダム）
user_id=1 → id=843   ──────→  843番の行を探して status 等を読む
user_id=1 → id=12904 ──────→  12904番の行を探して読む
user_id=2 → id=77    ──────→  77番へ飛んで読む
...×500,000
```

### 対比

| | `COUNT(*)` | `SELECT * ORDER BY user_id` |
|---|---|---|
| 必要な列 | なし（件数だけ） | 全列 |
| インデックスで完結するか | する（カバリング） | しない → 回表が必要 |
| 本体アクセス | 0回 | 50万回・ランダム |
| 読み方 | シーケンシャル | ランダムジャンプ |
| `Extra` | `Using index` | （なし＝本体を読んでいる印） |

MySQL は実際には後者で `type: index` を嫌い、`ALL`（全走査）＋ `Using filesort` を選ぶことも多い。
「インデックスを使う＝速い」ではなく、**そのインデックスだけで必要な列が揃うか** が分かれ目。

## Q5. `SELECT * FROM orders ORDER BY user_id` を速くするには

このクエリは「全50万行・全列・ソート付き」を要求している。
「速くする」より「クエリを現実的な形に変える」のが正解。効果が大きい順。

### 1. `LIMIT` を付ける（ページング）― 最も効く

```sql
SELECT * FROM orders ORDER BY user_id LIMIT 50;
-- 続きは WHERE user_id > (前ページ最後の値) ... LIMIT 50（キーセットページング）
```

`user_id` にインデックスがあれば、インデックスを先頭から50件なぞって止まる。回表も50回で済む。

### 2. `WHERE` で絞る

```sql
SELECT * FROM orders WHERE user_id = 100 ORDER BY user_id;
```

`user_id` のインデックスで数件に絞れる（`type: ref`）。
しかも `user_id` で絞ると結果は元々 `user_id` が一定なので、ソート自体が消える（`Using filesort` が出ない）。

### 3. カバリングインデックス（全列を諦めるなら）

```sql
ALTER TABLE orders ADD INDEX ix_cover (user_id, status);
SELECT user_id, id, status FROM orders ORDER BY user_id;  -- Using index、回表ゼロ
```

`SELECT *`（全列）でこれをやると、インデックスがテーブルの丸コピーになり容量倍増・書き込み遅化。
後で列を1つ足すとカバリングが崩れる。現実的でないことが多い。

### 4. 全行・全列が本当に必要なら、`ALL` + filesort を受け入れる

バッチ処理などで50万行すべてを `user_id` 順に取り出す必要が本当にあるなら、インデックスは使わない方が速い。

- 本体を全走査（シーケンシャル読み込み）
- メモリ上で50万行をソート（`Using filesort`）

これが `type: index` + 50万回ランダム回表より速い。オプティマイザも普通この計画を選ぶ。
できる対策は `sort_buffer_size` を十分に取ってソートがディスクにあふれないようにするくらい。

| 状況 | 打ち手 |
|---|---|
| 画面表示・API | `LIMIT` + キーセットページング（`WHERE user_id > ?`）＋ `user_id` インデックス |
| 特定ユーザーの注文 | `WHERE user_id = ?`（ソートも消える） |
| 必要な列が少数 | その列だけのカバリングインデックス |
| バッチで全件必要 | 諦めて `ALL` + filesort。`sort_buffer_size` を確保 |

## Q6. セカンダリインデックスとは

InnoDB のテーブルには **クラスタインデックス（＝主キー）が必ず1個** あり、
テーブルの行データそのものがその中に主キー順で並んで格納されている。「テーブル＝主キーのインデックス」。

**それ以外に自分で作るインデックスは全部「セカンダリインデックス」**（二次索引・非クラスタインデックス）。
`ALTER TABLE ... ADD INDEX` や `UNIQUE` で作るものはすべてこれ。

### 中身の違い

```
■ クラスタインデックス（主キー = テーブル本体）   id順
  id=1  | user_id=100 | status=paid | total_amount=3000 | created_at=...
       └─ 全列がここに揃っている

■ ix_user_id（セカンダリインデックス）           user_id順
  user_id=100 → id=1
  user_id=100 → id=3
       └─ 入っているのは「張った列(user_id)」＋「主キー(id)」だけ
```

セカンダリインデックスは独立した B+木で、張った列で並び替えられている。
ただし葉に持っているのはインデックス列の値と主キーの値だけ。他の列は入っていない。

### だから何が起きるか

| 事柄 | 理由 |
|---|---|
| **回表（bookmark lookup）が要る** | 他の列が欲しいと、葉にある主キーを使ってクラスタインデックスを引き直す |
| **主キーは小さくすべき** | 主キーの値が全セカンダリインデックスの葉にコピーされる。主キーが巨大だと索引が全部太る |
| **カバリングインデックスが速い** | 必要な列が全部セカンダリインデックスの中に収まれば、回表ゼロで完結（`Using index`） |
| **主キー検索が最速な理由** | クラスタインデックスを引いた時点で全列がそこにある。回表が構造的に発生しない |

### 用語の対応

| 呼び方 | 実体 | EXPLAIN の `key` |
|---|---|---|
| クラスタインデックス／主キーインデックス | テーブル本体そのもの | `PRIMARY` |
| セカンダリインデックス／二次索引／非クラスタインデックス | 別途の B+木（列＋主キー） | 自分で付けたインデックス名（例 `ix_user_id`） |

## Q7. `Backward index scan` と `Using filesort` とは

どちらも `ORDER BY` をどう処理したかを示す `Extra` の表示。
Stage 1 末尾の2クエリがちょうどこの対比になっている。

### Using filesort ＝「別途ソートした」

インデックスから並んだ順で行を取れないので、行を集めてから改めて並べ替えた、という意味。

名前に注意 ― "filesort" でも必ずファイルを使うわけではない。

- 結果が小さい → `sort_buffer_size` の範囲でメモリ内ソート
- 結果が大きい → あふれた分をディスクの一時ファイルに書いてマージソート（本当に遅いのはこっち）

出るのはどんなときか。

- `ORDER BY` の列にインデックスが無い
- `WHERE` が別のインデックスを使っていて、その並びが `ORDER BY` と合わない
- JOIN の結果を並べ替える
- 複合インデックスの並び順と `ORDER BY` の向き・列順がずれる

```sql
EXPLAIN SELECT * FROM orders ORDER BY total_amount DESC LIMIT 10;
```

`total_amount` に索引が無い → `type: ALL` ＋ `Using filesort`。
50万行を全部読んでソートし、上位10件を返す。
（`LIMIT` が付くと「上位N件だけ保持する優先度キュー方式」に切り替えて多少軽くするが、
入力の50万行を読むこと自体は変わらない。）

避け方：`ORDER BY` する列にインデックスを張る。
あるいは `WHERE` と `ORDER BY` を同じインデックスで賄えるように複合インデックスを設計する（Stage 4）。

### Backward index scan ＝「インデックスを逆からたどった」

B+木の葉（末端）は双方向リンクでつながっている。昇順にも降順にもたどれる。
だから `ORDER BY 列 DESC` でその列にインデックスがあれば、
末尾から先頭へなぞるだけで降順の結果が得られる。ソート不要 → `Using filesort` は出ない。

```sql
EXPLAIN SELECT * FROM orders ORDER BY id DESC LIMIT 10;
```

主キーインデックスは `id` 昇順に並んでいる。それを逆から10件たどって終わり。
`type: index` ＋ `Backward index scan`、`Using filesort` なし。

コストは前向きスキャンよりわずかに不利（ディスクの先読みが効きにくい程度）だが、
filesort に比べれば桁違いに軽い。
MySQL 8.0 からの最適化で、8.0 では `INDEX (col DESC)` という降順インデックス自体も定義できる。

### 3つのパターンを並べて

| クエリ | `type` | `Extra` | 中身 |
|---|---|---|---|
| `ORDER BY id LIMIT 10` | `index` | （なし） | 主キー索引を前から10件 |
| `ORDER BY id DESC LIMIT 10` | `index` | `Backward index scan` | 主キー索引を後ろから10件。ソート不要 |
| `ORDER BY total_amount DESC LIMIT 10` | `ALL` | `Using filesort` | 全行読んで並べ替え、上位10件 |

見分けの要点：`ORDER BY` の列がインデックスの並びと一致していれば `filesort` は消える。
`DESC` でも逆走でカバーできる。一致しなければ `filesort` が出て、件数が多いほど高くつく。

## Q8. 主キーが `ORDER BY` に使われるとソートは行われるのか（主キーと索引の使われ方の違い）

### 結論

`ORDER BY id DESC LIMIT 10` では **ソート（filesort）は行われない**。`Using filesort` も出ない。

InnoDB では主キーもインデックスの一種（クラスタインデックス）で、
テーブルの行が `id` 昇順に並んだ B+木として物理的に格納されている。
`ORDER BY id` は「すでに `id` 順に並んでいる木をなぞるだけ」、`DESC` なら「その木を末尾からなぞるだけ」。
並べ替える作業がそもそも発生しない。

「主キーが `ORDER BY` に使われる」＝「インデックスが `ORDER BY` に使われる」で同じ仕組み。
主キーだから特別にソートが起きる、ということはない。

### ソートが行われるかどうかの判定基準

> `ORDER BY` の並び順を、あるインデックス（クラスタインデックス含む）を
> 前向き or 後ろ向きになぞるだけで再現できるか？

- できる → ソート不要（`Backward index scan` が出ることはある）
- できない → `Using filesort`

`ORDER BY total_amount` は `total_amount` のインデックスが無いので再現不可 → filesort。

### 主キー と セカンダリインデックスの使われ方の違い

`ORDER BY` に関しては「順序を供給する」役割は両者とも同じ。違いは **他の列を取るときのコスト**。

| | `ORDER BY id`（主キー） | `ORDER BY user_id`（セカンダリ）＋`SELECT *` | `ORDER BY total_amount`（索引なし） |
|---|---|---|---|
| filesort | 不要 | **不要**（索引が順序を供給する） | 必要 |
| 回表 | **発生しない**（葉に全列がある） | **1行ごとに発生** | ―（そもそも全走査） |
| `type` | `index` | `index`（ただし高コスト） | `ALL` |
| `LIMIT 10` を付けた場合 | 10行なぞって終了・高速 | 10回だけ回表して終了・高速 | 全行読んでソートし上位10件 |
| `LIMIT` なし・全件 | 全件シーケンシャル・そこそこ速い | 50万回のランダム回表 → オプティマイザは嫌って `ALL`＋filesort を選びがち | 全走査＋filesort |

- **主キーで `ORDER BY`**：クラスタインデックスの葉に全列が入っているので、なぞるだけで完結。
  回表もソートも無い。だから `ORDER BY id DESC LIMIT 10` は無条件に速い。
- **セカンダリインデックスで `ORDER BY`**：インデックスをなぞる時点で順序は手に入る（ソートは要らない）。
  ただし `SELECT *` だと足りない列を取りに回表が要る。件数が多いとこの回表が高コストになり、
  結果的にオプティマイザが「インデックスを使わず全走査してメモリでソート」を選ぶことがある。
  これが `ORDER BY user_id`（`LIMIT` なし）が `ALL`＋`Using filesort` になる正体。

### 整理

1. `ORDER BY` でソートが要るかは「その並びをインデックスの走査で作れるか」だけで決まる。主キーか否かは関係ない。
2. 主キー（クラスタインデックス）は葉に全列があるので、`ORDER BY 主キー` は回表ゼロで常に軽い。
3. セカンダリインデックスも順序は供給できる（ソートは不要）が、`SELECT *` だと回表コストが乗る。
   そのコスト次第でオプティマイザが filesort 付きの全走査に切り替える。
4. `LIMIT` が付くと「なぞって途中で止まる」が効くので、セカンダリインデックス経由でも速くなる。

## Q9. B+木とは何か（イメージで）

MySQL のインデックスはすべて「B+木」という木構造でできている。
細かい定義より、**動きのイメージ**をつかむのが目的。

### 一言でいうと

**「県 → 市 → 番地」で住所をたどるのと同じ。**
上から順に「どっちの枝か」を選んでいくと、何百万件あっても数回で目的の1件に着く。

### 特徴（ここは軽く）

- 枝分かれがものすごく多い（1つの分かれ道に数百〜千の行き先）。だから木がとても低い。
- 実データは一番下の段（葉）にだけ並ぶ。上の段は「道案内の看板」だけ。
- 葉は左から右へキーの小さい順に並び、隣どうしが手をつないでいる（前後にたどれる）。
- どの葉も同じ深さ。だから「どの行を探しても手間は同じ」。

---

### 具体例1：`WHERE id = 372918` を探す道のり

`orders` は50万行。主キー `id` のB+木はこうなっている（数字はイメージ）。

```
【1段目：根】ページを1枚読む
  ┌─────────────────────────────────────────┐
  │ ~166000 → 左   ~333000 → 中   333001~ → 右 │
  └─────────────────────────────────────────┘
        372918 は「右」                         ↓
【2段目：内部ノード】ページをもう1枚読む
  ┌─────────────────────────────────────────┐
  │ ~350000 → A   ~380000 → B   380001~ → C   │
  └─────────────────────────────────────────┘
        372918 は「B」                          ↓
【3段目：葉】ページをもう1枚読む
  ┌──────────────────────────────────────────────┐
  │ id=372901 | 372902 | ... | 372918 ★ | ... 372950 │
  │  ↑ この葉に id と一緒に「その行の全列」が入っている  │
  └──────────────────────────────────────────────┘
```

**ページ読み込み3回で到着。** 50万行を1件ずつ見れば最悪50万回なので、けた違いに速い。
行数が5000万に増えても、段数が1つ増えて4回になる程度。これが `type: const` が一瞬で終わる理由。

---

### 具体例2：`WHERE id BETWEEN 372918 AND 372950` の範囲検索

まず 具体例1 と同じ手順で `372918` の葉まで下りる（3回）。
あとは **葉の中を右へ読んでいくだけ**。葉をまたぐときは、手をつないだ隣の葉へ移るだけで根に戻らない。

```
葉A [..372918★..372950] ⇄ 葉B [372951..373120] ⇄ ...
     └──ここを右へ舐めるだけ──┘
```

「入口まで木を下りる」＋「あとは葉を横に舐める」。これが `type: range` の正体。

---

### 具体例3：`ORDER BY id LIMIT 10` と `ORDER BY id DESC LIMIT 10`

葉はもともと `id` 順に並んでいる。だから**並べ替え作業（filesort）は不要**。

```
昇順： 葉の左端から  [1,2,3,...] → 10件取ったら終了
降順： 葉の右端から  [...,499999,500000] を逆にたどる → 10件取ったら終了
       └ 葉が前後どちらにもたどれるから、DESC でもソート要らず（Backward index scan）
```

---

### 具体例4：セカンダリインデックスだと葉の中身が違う

`ADD INDEX ix_user_id (user_id)` を張ると、**もう1本別のB+木**ができる。
形（根・内部・葉）は同じだが、**並び順は `user_id` 順**で、**葉に入っているのは `user_id` と `id` だけ**。

```
ix_user_id の葉：
  user_id=100 → id=1    | user_id=100 → id=3   | user_id=101 → id=88 | ...
                                                 └ status も total_amount も入っていない
```

だから `SELECT * FROM orders WHERE user_id = 100` は：

1. `ix_user_id` の木を下りて、`user_id=100` の葉に着く（`id=1, 3` が分かる）
2. その `id` を持って、**主キーのB+木（具体例1の木）を下り直して** 全列を取る ← これが「回表」

木を「2本」たどることになる。件数が多いほど 2 が積み重なって重くなる。

---

## Q10. インデックスごとに [根・内部ノード・葉] のワンセットが作られるのか

そのとおり。**インデックス1つ ＝ 独立したB+木が1本まるごと。**

### 具体例：`orders` にインデックス3つ

```sql
PRIMARY KEY (id)
ADD INDEX ix_user_id (user_id)
ADD INDEX ix_status  (status)
```

ディスク上にB+木が **3本** できる。

```
① 主キーの木（id順）      根─内部─葉[ id順に「行の全列」が並ぶ ]  ← これがテーブル本体
② ix_user_id の木（user_id順） 根─内部─葉[ (user_id, id) だけ ]
③ ix_status の木（status順）   根─内部─葉[ (status, id) だけ ]
```

同じ行の情報が、木ごとに違う順番で・必要な列だけ、重複して持たれている。

### ここから分かること

| 事柄 | 理由（イメージ） |
|---|---|
| インデックスを増やすと `INSERT` が遅くなる | 1行追加するたびに、3本の木すべてに葉を差し込む |
| `status` を `UPDATE` → ①と③を更新／`total_amount` を `UPDATE` → ①だけ | 変えた列に対応する木だけ書き直す |
| 主キー `id` の変更は激重 | ②③の葉にも `id` がコピーされているので、全部書き換えになる（だから主キーは変えない） |
| `SELECT COUNT(*)` は ② か ③ を使う | 葉が `(列, id)` だけの ②③ は ① より小さい。数えるだけなら小さい木が速い |
| 回表 ＝ 木をもう1本下りること | ②の葉で `id` を得て、①を根から下り直す |

### 補足：インデックスの貼られた列を更新するのはやや重い

上の表の「`status` を `UPDATE` → ①と③」がなぜ「やや重い」のか。
**インデックスなしの列は「書き換えるだけ」、インデックスありの列は「木の中で引っ越し」だから。**

| | やること |
|---|---|
| `total_amount`（索引なし）を更新 | ①の葉の該当箇所の数字を**上書きするだけ**。木1本・多くはページ1枚 |
| `status`（索引あり）を更新 | ①を上書き。**加えて** ③では並び順が `status` で決まっているので、値が変わると居場所が変わる → **古いエントリを消して新しい位置に入れ直す**（別ページ・ページ分割もありうる） |

```
status を 'new' → 'paid' に更新

① 主キーの木： 葉の該当行の status 欄を 'new' → 'paid' に上書き（1箇所）

③ ix_status の木：
   before  [ ... new, new, new | paid, paid ... ]
                        ↑ここから抜いて
   after   [ ... new, new | paid, paid, paid ... ]
                            ↑ここへ挿す（＝引っ越し）
```

`orders.status` は `new → paid → shipped → delivered` と何度も変わる列。
`ix_status` を貼っていると、**1回の状態遷移ごとに ③ で「消して入れ直す」が発生**する。
50万件が各3〜4回遷移すれば ③ への書き込みは150万〜200万回。
「未発送一覧を毎分引くから `WHERE status = 'new'` を速くしたい」という**読みの利益**と、この**書きのコスト**を天秤にかける。

特に重くなるのは次の場合。

- 更新する列が**複数のインデックスに登場**（`(status)` と `(status, created_at)` の両方があれば木2本を引っ越し）
- 更新する列が**主キーの一部**（上の表のとおり全セカンダリの葉も書き換え。別次元に重い）
- **更新頻度が非常に高い列**にインデックス（`last_login_at`、カウンタ、ステータスフラグ）

指針：**クエリで絞る・並べる必要が本当にある列だけ**にインデックスを貼る。
`UPDATE` 文では**実際に変わった列だけ**を `SET` する。
非インデックス列の更新は軽い／インデックス1本に載る列はやや重い／主キーの更新は別次元、という感覚を持っておく。
ふつうの業務テーブルで数本のインデックスなら過度に恐れる必要はなく、効くのは高頻度更新 × 高書き込み量のとき。

### 複合インデックスは「1本」

`ADD INDEX ix_a_b_c (a, b, c)` は木3本ではなく **1本**。
`(a, b, c)` をひとかたまりのキーにして並んだ、単一のB+木。
電話帳が「姓 → 名」の順で並ぶのと同じで、`姓` からは引けるが `名` だけでは引けない。
→ 複合インデックスは左から順にしか使えない、という Stage 4 の話につながる。
