# Stage 3: N+1問題とアンチパターン

## 概要/ゴール

「動くけど遅いSQL」には典型的なパターンがある。このステージでは代表的な4つの
アンチパターン（N+1問題、先頭ワイルドカードLIKE、インデックス列への関数適用、SELECT *）を
実際に体験し、それぞれの原因と対策を理解する。

## 前提知識

[Stage 2: インデックスの基礎](../02_index_fundamentals/README.md) が完了し、
`users.email` と `orders.user_id` にインデックスが作成済みであること。

## 事前準備

```sql
SHOW INDEX FROM users;
SHOW INDEX FROM orders;
```

`idx_users_email`, `idx_orders_user_id` が存在することを確認する。

## 悪いクエリを実行してEXPLAINを見る

`exercise.sql` の課題1にあるシェルコマンドを実際にターミナルで実行してみる。

```bash
time (for i in $(seq 1 100); do
  docker compose exec -T mysql mysql -uroot -prootpass sqltuning \
    -e "SELECT * FROM order_items WHERE order_id = $i;" > /dev/null
done)
```

これは「注文一覧を取得したあと、注文ごとに明細を1件ずつ取りに行く」という
アプリケーションコードでありがちな実装（N+1問題）を疑似的に再現したもの。
1件ずつのSELECT自体はインデックス（主キー相当）で高速に終わるが、
「クエリを100回発行する」こと自体にコストがかかる。

## 課題

`exercise.sql` に沿って、以下の4つを確認する。

1. **N+1問題**: ループでの100回クエリ vs `BETWEEN`でまとめた1回のクエリの実行時間比較
2. **先頭ワイルドカードLIKE**: `LIKE 'xxx%'`（前方一致）と `LIKE '%xxx'`（先頭%）でtypeがどう変わるか
3. **インデックス列への関数適用**: `YEAR(created_at) = 2024` と `created_at >= '...' AND < '...'` の比較
4. **SELECT \***: 必要な列だけを取るクエリとの違いを考える

**達成基準**:
- N+1のシェル実行と1回クエリの実行時間の差を、実際の秒数で確認できること
- 課題2, 3で「インデックスが使われるパターン」と「使われないパターン」をそれぞれ再現できること

## 解説

### なぜN+1が問題なのか

1件あたりのクエリが速くても、クエリの発行回数が増えるとその分だけ
「ネットワーク往復」「コネクション処理」「SQLパース」などの**固定オーバーヘッド**が
積み重なる。100回のループと1回のIN句/JOINでは、この固定オーバーヘッドの回数が
100倍違う。「クエリ自体の実行速度」だけでなく「クエリの発行回数」もチューニング対象。

### インデックスが使われない書き方の共通点

先頭ワイルドカードLIKEも、インデックス列への関数適用も、根本原因は同じ:
**インデックスは「ソート済みの値」を前提に高速化する仕組みなので、
検索条件を「インデックスに入っている値そのもの」と比較する形にしないと機能しない。**

- `LIKE '%xxx'` → 「どの値から始まるか」が分からず、ソート順を辿れない
- `YEAR(created_at) = 2024` → インデックスには「関数を通す前の日時」が入っているため、
  関数を通した後の値では照合できない

対策の型は共通していて、「列そのものを比較する形に書き換える」こと。
