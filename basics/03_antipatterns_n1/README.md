# Stage 3: N+1問題とアンチパターン

## このステージでわかること

「動くけど遅いSQL」には、繰り返し出てくる決まった失敗パターン（アンチパターン）がある。
このステージでは代表的な4つ——**N+1問題**、**先頭ワイルドカードLIKE**、
**インデックス列への関数適用**、**SELECT \***——を実際に動かして、
なぜ遅いのか・どう書けば直るのかを理解する。

## 前提

[Stage 2: インデックスの基礎](../02_index_fundamentals/README.md) が終わり、
`users.email` と `orders.user_id` にインデックスがある状態。確認する。

```sql
SHOW INDEX FROM users;   -- idx_users_email がある
SHOW INDEX FROM orders;  -- idx_orders_user_id がある
```

## パターン1: N+1問題

### どんな問題？ ― 身近な例えで

スーパーで10品を買うとき、1品ごとにレジに並び直して会計する人はいない。
カゴにまとめて1回で会計する。1回の会計には「レジに移動する」「店員とやり取りする」という
**固定の手間**があり、10回に分ければその手間が10倍かかるからだ。

アプリケーションでも同じことが起きる。「注文一覧を取得したあと、注文ごとに明細を1件ずつ
取りに行く」という実装をすると、注文が100件あればSQLを **1 + 100回** 発行することになる。
これを **N+1問題** と呼ぶ。1回1回のSQLはインデックスで高速に終わっても、
「SQLを発行する」こと自体の固定コスト（ネットワーク往復・接続処理・SQLのパース）が
100回積み上がる。

### まず現状を見てみる

ターミナル（MySQLプロンプトではなく、通常のシェル）で次を実行する。
注文ID 1〜100 の明細を、1件ずつ100回に分けて取りに行く「N+1の再現」である。

```bash
time (for i in $(seq 1 100); do
  docker compose exec -T mysql mysql -uroot -prootpass sqltuning \
    -e "SELECT * FROM order_items WHERE order_id = $i;" > /dev/null
done)
```

### こう直す（指示）

100回のSELECTを、範囲条件で1回にまとめる。

```sql
SELECT * FROM order_items WHERE order_id BETWEEN 1 AND 100;
```

アプリ側で取得済みのIDリストを渡すなら `IN` でもよい。

```sql
SELECT * FROM order_items WHERE order_id IN (1, 2, 3, /* ... */ 100);
```

**【目的】** 「SQLを発行する固定コスト」を100回分から1回分に減らす。

### 結果の見方 ― 何が変わったか

実測の一例（環境で変動するが、桁が変わるほどの差が出る）:

| 方法 | 所要時間の目安 |
|---|---|
| ループで100回、個別にクエリ | 約88秒 |
| 1回のクエリにまとめる | 約0.9秒 |

**【変わった点】** 取得しているデータの中身は同じなのに、実行時間が約100倍違う。
違いは「クエリの発行回数」だけ。

**【なぜ速くなったか】** 個々のSQLが速くても、発行のたびに接続処理・ネットワーク往復・
パースという固定オーバーヘッドがかかる。1回にまとめれば、この固定費は1回分で済む。
実務では **JOIN で必要なデータを1度に取る** か、**IN句でまとめて取る**（ORMの
eager loading もこの仕組み）で回避する。「1クエリの速度」だけでなく
「クエリの発行回数」もチューニングの対象になる。

## パターン2: 先頭ワイルドカードLIKE

### どんな問題？ ― 身近な例えで

電話帳（姓の五十音順）で「"田" で始まる姓」はすぐ引ける。並び順をたどればよい。
だが「"田" で**終わる**姓（山田、太田、…）」を探せと言われたら、
並び順は何の役にも立たず、1ページ目から全部見るしかない。

`LIKE` も同じ。`'user012345%'`（前方一致）は索引の並び順をたどれるが、
`'%johndoe@example.com'`（先頭が `%`）は「どの文字から始まるか」が不明なので索引を活かせない。

### まず見てみる

```sql
EXPLAIN SELECT * FROM users WHERE email LIKE 'user012345%';         -- 前方一致
EXPLAIN SELECT * FROM users WHERE email LIKE '%johndoe@example.com'; -- 先頭に%
```

### 結果の見方

| クエリ | `type` | `key` | 説明 |
|---|---|---|---|
| `LIKE 'user012345%'` | `range` | `idx_users_email` | 「`user012345` で始まる範囲」を索引でたどれる |
| `LIKE '%johndoe@example.com'` | `ALL` | `NULL` | 開始位置が不明で索引を使えず、全行スキャン |

**【対策】** 検索要件を前方一致で表せないか見直す。中間一致・後方一致がどうしても必要なら、
全文検索（`FULLTEXT` インデックス）や検索エンジン（Elasticsearch等）の導入を検討する。

## パターン3: インデックス列に関数をかけてしまう

### どんな問題？ ― 身近な例えで

索引は「元の言葉」で並んでいる。なのに「その言葉をすべて英訳した結果」で引こうとすると、
索引の並びとは対応しないので使えない。

日付列も同じ。`created_at` の索引には「変換前の日時」がそのまま並んでいる。
`YEAR(created_at) = 2024` と書くと「関数を通した後の値（年）」で照合することになり、
索引の並びと噛み合わず、全行スキャンになってしまう。

### まず見てみる

`created_at` にインデックスを追加してから、同じ「2024年6月」を2通りの書き方で比較する。

```sql
CREATE INDEX idx_orders_created_at ON orders(created_at);

-- 書き方A: 列に関数をかける
EXPLAIN SELECT * FROM orders
WHERE YEAR(created_at) = 2024 AND MONTH(created_at) = 6;

-- 書き方B: 列そのものを範囲で比較する
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2024-06-01' AND created_at < '2024-07-01';
```

### 結果の見方 ― 何が変わったか

| 書き方 | `type` | `key` | `rows` |
|---|---|---|---|
| A: `YEAR()/MONTH()` | `ALL` | `NULL` | 約498,000（全行） |
| B: 範囲条件 | `range` | `idx_orders_created_at` | 約38,000 |

**【変わった点】** 絞り込んでいる期間は同じ「2024年6月」なのに、
**列そのものを比較する形に書き換えただけ**で索引が使われ、調べる行数が1桁以上減った。

**【教訓】** WHERE句の中で、インデックスを効かせたい列に関数や計算を適用しない。
日付の年月検索は「範囲条件」に書き換えるのが定石。

## パターン4: SELECT * の問題

### まず見てみる

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
EXPLAIN SELECT id, status FROM orders WHERE user_id = 100;
```

### 結果の見方

EXPLAIN上の `type` / `rows` は、`SELECT *` でも `SELECT id, status` でも
大きくは変わらない（行の探し方自体は同じ）。しかし `SELECT *` には次のコストがある。

- **転送量**: 不要な列（`TEXT` 型の長いカラムなど）まで読んで転送し、ネットワーク帯域を消費する
- **カバリングインデックスの機会損失**: 必要な列だけなら、インデックスの情報だけで
  結果を返せて**テーブル本体を読まずに済む**ことがある。`SELECT *` だとその恩恵を捨てることになる（Stage 4）
- **変更に弱い**: テーブルに列が追加されたとき、アプリ側が想定外の列を受け取る

**【教訓】** 必要な列だけをSELECTする習慣が、将来のチューニングの選択肢（特にカバリングインデックス）を残す。

## インデックスが効かない書き方の共通点

先頭ワイルドカードLIKEも、インデックス列への関数適用も、根っこは同じ。

> インデックスは「並べ替え済みの値」を前提に速さを稼ぐ仕組み。
> 検索条件を「インデックスに入っている値そのもの」と比較する形にしないと機能しない。

対策の型も共通で、「**列そのものを、そのままの形で比較する**」ように書き換えること。

## まとめ

- **N+1**: SQLの発行回数も遅さの原因。JOIN や IN でまとめる
- **先頭ワイルドカードLIKE**: `'%...'` は索引を使えない。前方一致に寄せるか全文検索を検討
- **関数適用**: `YEAR(col) = ...` はNG。`col >= ... AND col < ...` の範囲条件に書き換える
- **SELECT \***: 動くが、転送量とカバリングインデックスの面で損。必要な列だけ取る

## さらに詳しく

次の2つはインデックスが使われるか。予想してから実行すると、パターンの理解が固まる。

```sql
EXPLAIN SELECT * FROM orders WHERE created_at = '2024-06-15 00:00:00';
EXPLAIN SELECT * FROM users WHERE UPPER(email) = 'USER012345.JOHNDOE@EXAMPLE.COM';
```

- 1つ目 … 列に関数をかけていない等値比較なので、`idx_orders_created_at` が使われる（`type: ref`）。
- 2つ目 … `UPPER(email)` と、列に関数をかけているのでパターン3と同じ。
  `idx_users_email` は使えず `type: ALL` になる。
  大文字小文字を無視した検索がしたいなら、照合順序（collation）の設定や、
  小文字化した値を格納する専用列＋そこへの索引、といった設計で対応する。
