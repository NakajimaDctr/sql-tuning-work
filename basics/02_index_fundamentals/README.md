# Stage 2: インデックスの基礎

## 概要/ゴール

Stage 1で「インデックスがないと遅い」ことを確認した。このステージでは実際に
`CREATE INDEX` でインデックスを追加し、EXPLAINの結果がどう変わるかを自分の手で確認する。
インデックスの仕組み（B-Tree）と、トレードオフ（書き込みコスト・ストレージ）も理解する。

## 事前準備

Stage 1の時点では `users`, `orders` に主キー以外のインデックスはない状態のはず。
確認する場合は次を実行する。

```sql
SHOW INDEX FROM users;
SHOW INDEX FROM orders;
```

`PRIMARY` 以外の行が出てこなければOK。

## 悪いクエリを実行してEXPLAINを見る

Stage 1でも見た以下のクエリを再確認する。

```sql
EXPLAIN SELECT * FROM users WHERE email = 'user012345.johndoe@example.com';
```

`type: ALL` で約48,000行を全部確認していることを再確認する。

## 課題

1. `users.email` と `orders.user_id` に、それぞれ適切なインデックスを `CREATE INDEX` で作成せよ。
2. インデックス作成後、同じクエリを再度EXPLAINし、`type` が `ALL` から変わること、
   `rows` が大幅に減ることを確認せよ。

`exercise.sql` に沿って進めること。

**達成基準**:
- `users WHERE email = '...'` の `type` が `ref` または `const` になること

## 解説

### インデックスの仕組み

MySQL（InnoDB）のインデックスはB-Tree（多分岐の平衡木）で実装されている。
列の値をあらかじめソートして保持しておくことで、目的の値への到達を
「全件確認（線形探索）」から「木を辿るだけ（対数時間に近い探索）」に変える。

イメージ:
```
インデックスなし: [行1][行2][行3]...[行48999][行49000]  <- 先頭から順に確認 (最悪48,999回比較)
インデックスあり: ソート済みの木構造を辿って一発で目的の値の位置にたどり着く
```

### インデックスのコスト

インデックスは無料ではない。

- **ストレージ**: インデックス自体もディスク上にデータ構造として保存される
- **書き込みコスト**: `INSERT`/`UPDATE`/`DELETE` のたびに、テーブル本体だけでなく
  インデックスも更新する必要がある。インデックスが多いほど書き込みは遅くなる

そのため「とりあえず全部の列にインデックスを張る」のは誤り。
**検索条件（WHERE, JOIN, ORDER BY）でよく使われる列**を優先してインデックスを検討する。

### なぜ Stage 0 の時点でインデックスがなかったのか

`00_schema.sql` は意図的に主キーのみで設計されている。実務でも「最初から
完璧なインデックス設計」は難しく、実際のクエリパターンを見てから
インデックスを追加・調整していくことが多い。このリポジトリではその過程を追体験する。
