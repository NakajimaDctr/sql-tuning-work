# Stage 7: ロックとトランザクション

## 概要/ゴール

これまでは「1つのクエリをいかに速くするか」を扱ってきたが、実際のアプリケーションは
複数のリクエストが同時にデータベースへアクセスする。このステージではInnoDBの
行ロック・ギャップロック・デッドロックを実際に体験し、なぜ「同時実行時に処理が
遅くなる/待たされる」ことが起きるのかを理解する。パフォーマンスチューニングは
「1クエリの速度」だけでなく「同時実行性(concurrency)」の観点も重要になる。

## 事前準備

このステージは**ターミナルを2つ**開く必要がある。それぞれで以下を実行し、
MySQLに接続した状態にしておく。

```bash
# ターミナルA
docker compose exec mysql mysql -uroot -prootpass sqltuning

# ターミナルB（別のターミナルウィンドウ/タブで）
docker compose exec mysql mysql -uroot -prootpass sqltuning
```

## 悪いクエリを実行してEXPLAINを見る

このステージはEXPLAINではなく「実際に2つのセッションを同時に動かして
待たされる様子を体感する」ことが目的。`exercise.sql`のシナリオ1をまず試す。

ターミナルAで:
```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 1;
```
（コミットせずそのまま待機）

ターミナルBで:
```sql
UPDATE orders SET status = 'cancelled' WHERE id = 1;
```

ターミナルBの応答が返ってこないはずである。これがロック待ちの状態。

## 課題

`exercise.sql`に記載された3つのシナリオを、指示された順番でターミナルA/Bに
交互に入力しながら進める。

1. **行ロック**: 同じ行への同時UPDATEがどう振る舞うか
2. **ギャップロック**: データが存在しない範囲でもロックされることがあるか
3. **デッドロック**: 互いにロックを取り合うとどうなるか

**達成基準**:
- シナリオ1で、Aがコミット/ロールバックするまでBの処理が止まることを体感する
- シナリオ3で、`ERROR 1213 (40001): Deadlock found ...` を実際に自分の画面で発生させる

## 解説

### 行ロック

InnoDBは変更対象の行に対して排他ロックをかける。ロックを保持しているトランザクションが
`COMMIT`または`ROLLBACK`するまで、他のトランザクションは同じ行への書き込みを待たされる。

### ギャップロック

MySQLのデフォルトの分離レベルは`REPEATABLE READ`。この分離レベルでは、
`SELECT ... FOR UPDATE`のような範囲検索で、実際にヒットする行がなくても
「値が存在しうる区間（ギャップ）」自体にロックがかかることがある。
これは「ファントムリード」（同じトランザクション内で同じ検索をしたのに
結果セットの行数が変わってしまう現象）を防ぐための仕組み。

```sql
SELECT @@transaction_isolation;  -- REPEATABLE-READ が確認できる
```

### デッドロック

2つ以上のトランザクションが互いに相手の持つロックを待ち合う状態。
InnoDBはこれを自動検知し、一方を強制的にロールバックしてエラーを返すことで解消する。
デッドロックはバグではなく、同時実行を許すシステムでは起こりうる正常な現象。
重要なのは「アプリケーション側でリトライできるように設計しておくこと」。

## 発展問題（任意）

現在のロック状況は`performance_schema.data_locks`で確認できる。
シナリオ1をもう一度実行し、Aがロールバックする前に、3つ目のターミナルから
以下を実行して、実際にどんなロックが張られているか覗いてみよう。

```sql
SELECT * FROM performance_schema.data_locks\G
SELECT * FROM performance_schema.data_lock_waits\G
```
