# Stage 7: ロックとトランザクション

## このステージでわかること

ここまでは「1つのクエリをいかに速くするか」を扱ってきた。だが実際のアプリケーションでは、
複数のリクエストが**同時に**データベースへアクセスする。
このステージでは InnoDB の **行ロック**・**ギャップロック**・**デッドロック** を
2つのセッションで実際に体験し、「同時実行時に処理が待たされる／遅くなる」のがなぜ起きるのかを理解する。
パフォーマンスは「1クエリの速度」だけでなく「同時実行性（concurrency）」の観点も重要になる。

## 前提

[Stage 6: 実行計画の内部を読む](../06_execution_plan_internals/README.md) が終わっていること。

このステージは **ターミナルを2つ** 開く。それぞれでMySQLに接続しておく。

```bash
# ターミナルA
docker compose exec mysql mysql -uroot -prootpass sqltuning

# ターミナルB（別のターミナルウィンドウ/タブで）
docker compose exec mysql mysql -uroot -prootpass sqltuning
```

以下、`[A]` `[B]` はどちらのターミナルで実行するかを表す。**指示された順番で交互に**入力していく。

---

## シナリオ1: 行ロック

### 身近な例えで

試着室に入ると鍵をかける。中の人が出てくる（＝トランザクションが `COMMIT` か `ROLLBACK` する）まで、
次の人はドアの前で待つしかない。エラーにはならない。ただ**待たされる**。

### 手順

```sql
-- [A]
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 1;
-- ここで COMMIT せず、そのまま放置する
```

```sql
-- [B]（Aがまだ COMMIT していない状態で実行）
UPDATE orders SET status = 'cancelled' WHERE id = 1;
-- → 応答が返ってこない（ブロックされる）。しばらく待って様子を見る
```

```sql
-- [A]（Bが止まっているのを確認したら）
ROLLBACK;
-- → この瞬間、[B] の UPDATE がようやく完了する
```

### 結果の見方

実測タイムスタンプの一例:

```
[B] UPDATE発行            : 14:36:10.815
[A] ROLLBACK実行          : 14:36:13.823
[B] UPDATE完了(ブロック解除): 14:36:13.825   ← Aのロールバックとほぼ同時
```

**【何が起きたか】** `[A]` が `UPDATE` で `id = 1` の行に**排他ロック**をかけ、
`COMMIT`/`ROLLBACK` するまで保持し続けた。その間、`[B]` が同じ `id = 1` を
`UPDATE` しようとすると、`[A]` がロックを手放すまで `[B]` は完全に停止する。
これが InnoDB の行ロックの基本動作。「同時実行だと遅い」の正体の一つ。

---

## シナリオ2: ギャップロック

### 身近な例えで

会議室の予約表で「14:00〜15:00 を仮予約中」の状態にすると、
その時間帯に他の人が予約を入れられない。**まだ誰も確定予約していない"空き時間"そのもの**を
押さえている。

### 手順

```sql
-- [A]
BEGIN;
SELECT COUNT(*) FROM orders
WHERE created_at BETWEEN '2030-01-01' AND '2030-01-02'
FOR UPDATE;
-- この期間には実際には1件もデータがない（空のギャップ）
```

```sql
-- [B]（Aがまだ COMMIT していない状態で実行）
INSERT INTO orders (user_id, status, total_amount, created_at)
VALUES (1, 'pending', 1000, '2030-01-01 12:00:00');
-- → 該当データが1件もないのに、なぜかブロックされる
```

```sql
-- [A]
ROLLBACK;
-- → [B] の INSERT が完了する
```

後片付け（`[B]` で実行）:

```sql
DELETE FROM orders WHERE created_at = '2030-01-01 12:00:00';
```

### 結果の見方

**【何が起きたか】** 対象範囲（2030-01-01〜02）には実データが1件もないのに、
`[B]` の `INSERT` はブロックされた。`SELECT ... FOR UPDATE` は、
該当する行だけでなく、その値の**"間"の区間（ギャップ）**にもロックをかけるためだ。

**【なぜこの仕組みが必要か】** MySQLのデフォルト分離レベルは `REPEATABLE READ`。

```sql
SELECT @@transaction_isolation;  -- REPEATABLE-READ
```

もしギャップロックがなければ、`[A]` のトランザクション中に `[B]` が同じ範囲へ新しい行を
`INSERT` して `COMMIT` でき、`[A]` が同じ `SELECT` をもう一度実行すると
**さっきはなかった行が見える**（＝**ファントムリード**という不整合）ことになる。
ギャップロックはこれを防いでいる。

---

## シナリオ3: デッドロック

### 身近な例えで

2人が、相手が握っている道具を「貸して」と言い合って、どちらも自分の道具を手放さない。
永遠に進まない。

### 手順

```sql
-- [A]
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 1;   -- id=1 をロック
```

```sql
-- [B]
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 2;   -- id=2 をロック
```

```sql
-- [A]（id=2 は B がロック中 → ブロックされる）
UPDATE orders SET status = 'paid' WHERE id = 2;
```

```sql
-- [B]（id=1 は A がロック中。かつ A は id=2 待ちで止まっている → 循環待ち）
UPDATE orders SET status = 'paid' WHERE id = 1;
```

最後に、両方のターミナルで `ROLLBACK;`（エラーになった側は既にロールバック済み）。

### 結果の見方

```
[A] id=1 をロック  → OK
[B] id=2 をロック  → OK
[A] id=2 を要求    → B が保持中のためブロック
[B] id=1 を要求    → A が保持中のためブロック（ここで循環待ちが成立）
数秒後、[B] 側でエラー:
  ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
[A] 側は直後にロックを取得して処理続行
```

**【何が起きたか】** InnoDB は定期的にロック待ちの関係をグラフとして監視しており、
循環待ち（デッドロック）を検知すると、**一方のトランザクションを強制的にロールバックして
エラーを返す**ことで膠着を解消する。どちらが犠牲（victim）になるかは
「ロールバックのコストが小さい方」＝一般に変更行数が少ない方が選ばれる。

**【実務での対策】**

- 複数の行／テーブルを更新するときは、**常に同じ順序**でロックを取る（例:「必ず id の昇順で更新する」）
- アプリ側でデッドロックエラー（`1213`）を検知したら、**トランザクションをリトライ**する実装にしておく
- トランザクションはできるだけ短く保つ（ロック保持時間を減らす）

デッドロックはバグではなく、同時実行を許すシステムでは起こりうる正常な現象。
「起きない前提」ではなく「起きてもリトライで回復できる前提」で設計する。

## まとめ

- **行ロック**: 変更中の行は、`COMMIT`/`ROLLBACK` まで他のトランザクションが待たされる
- **ギャップロック**: `REPEATABLE READ` では、行がない範囲でも区間ごとロックされ、ファントムリードを防ぐ
- **デッドロック**: 循環待ちをInnoDBが自動検知し、片方をロールバック。リトライ設計で対処する
- チューニングは「1クエリの速度」だけでなく「同時に走ったときの待ち」も対象

## さらに詳しく

いま張られているロックは `performance_schema` で確認できる。
シナリオ1をもう一度実行し、`[A]` が `ROLLBACK` する前に、**3つ目のターミナル**から見てみる。

```sql
SELECT * FROM performance_schema.data_locks\G
SELECT * FROM performance_schema.data_lock_waits\G
```

`data_locks` には、どのトランザクションがどの行に、どの種類（`RECORD`, `GAP` など）の
ロックを持っているかが並ぶ。`data_lock_waits` には「誰が誰の解放を待っているか」が出る。
シナリオ2で見れば `LOCK_MODE` に `GAP` が現れ、ギャップロックが実在することが確認できる。
