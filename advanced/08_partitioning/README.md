# Stage 8: パーティショニング

## 概要/ゴール

テーブルが非常に大きくなった場合、物理的にデータを分割して格納する
「パーティショニング」という選択肢がある。このステージではRANGEパーティションを
実際に作成し、「パーティションプルーニング」（不要なパーティションを
読み飛ばす最適化）を体験する。あわせて、パーティショニングが効くケースと
効かないケースの違いを理解する。

**重要**: このステージでは共有の `orders` テーブルを直接変更しない。
`orders_partitioned` という演習専用のコピーテーブルを作成して進める

## 悪いクエリを実行してEXPLAINを見る

パーティションを作る前に、通常の`orders`テーブルで日付範囲検索のEXPLAINを見ておく。

```sql
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2025-01-01' AND created_at < '2025-02-01';
```

`idx_orders_created_at`（Stage 3で作成済み）があれば`range`アクセスになるはずだが、
このステージでは「テーブル自体を物理的に分割する」アプローチを
インデックスとは別の観点として学ぶ。

## 課題

`exercise.sql`に沿って進める。

1. `created_at`の年でRANGEパーティショニングされた`orders_partitioned`を作成する
2. `orders`のデータをコピーし、各パーティションの件数を確認する
3. 日付範囲を条件にしたクエリと、パーティションキーに関係ない条件のクエリで
   `EXPLAIN`の`partitions`列を比較する
4. 演習後は`orders_partitioned`を削除する

**達成基準**:
- `created_at`で絞り込むクエリが特定のパーティションだけにアクセスすること
  （`partitions`列が全パーティションでないこと）を確認できること
- パーティションキーと無関係な条件（`user_id`）では全パーティションを
  見に行ってしまうことを説明できること

## 解説

### パーティションプルーニングとは

パーティション化されたテーブルに対してクエリを実行する際、MySQLは
「そもそもどのパーティションに該当データがある可能性があるか」を
WHERE句から判断し、関係ないパーティションへのアクセスを丸ごとスキップする。
これがEXPLAINの`partitions`列に反映される。

### 効果的なケース / そうでないケース

| ケース | プルーニングは効くか |
|---|---|
| パーティションキー(created_at由来)で範囲検索 | ○ 効く |
| パーティションキーと無関係な列(user_id)で検索 | × 効かない（全パーティション走査） |

日付・時系列データを「直近N日分だけ集計する」「古いデータを一括削除する」
といった用途では強力な選択肢になる一方、「そもそも何を軸に検索することが多いか」を
見極めずに導入すると効果が出ない、あるいはむしろオーバーヘッドになる。

### インデックスとの役割の違い

パーティショニングは「大きな塊を事前に絞り込む」仕組みであり、
パーティション内部の検索には引き続きインデックスが必要になる。
両者は排他的ではなく、組み合わせて使うのが一般的。

## 発展問題（任意）

`ALTER TABLE orders_partitioned DROP PARTITION p2024;` を実行すると
2024年分のデータが一括で削除される。`DELETE FROM ... WHERE YEAR(created_at) = 2024`
と比べて、どちらが高速か・どちらが安全かを考えてみよう
（試す場合は演習用テーブルの上で行うこと）。
